# paseo-orbi operator guide

Operational detail for [paseo-orbi](../README.md): authorization, data flow and permissions, repair codes, observation limits and installation preparation. Read the [README](../README.md) first for what the plugin is and how to start. Paseo plugin contracts live in [the development reference](paseo-plugins.md); the installed qualification harness lives in [testing/qualification.md](testing/qualification.md).

## Status

**Status:** Issues browsing and trusted report reading are implemented. **Work** opens on the selected repository's issue rows and label chips. **Services** is the host-scoped service screen and the default landing for a host without linked repositories: every observed group is listed failures first, without accordions, and **Details** opens a separate host-scoped view that leads with the service display name, its failed-first slot facts and freshness, and offers **View diagnostics** for the raw unit data, plus Start/Stop/Restart only for a deployment an operator explicitly granted controls on ([service controls](#service-controls-operator-grant-default-off)). Work keeps configured deployments, one selected deployment's timers/services, recorded health and one explicit presence/type check of an optional designated shortcut under **Configured repositories**. Runs adds attributed run/session metadata, structured events and PR/head-check evidence. Blockers explains trusted failures, waits and stat-only evidence without executing recovery. The deployment selector and rejected-deployment cards use the safe `deployments.list` catalog. Assembled offline checks cover Work, Services, Issues, Runs and Blockers through their real registrations, schemas and adapters. The tracked Git artifact is checked with isolated production-only preparation. This is installation readiness, not deployment; live installation and physical-client qualification remain unperformed.

The plugin observes; it does not plan or execute work:

- **Kit** plans work and creates GitHub Issues.
- **Orbi** owns execution, recovery, code review, and PR delivery.
- **Paseo** observes that work. This plugin is not another scheduler or orchestrator. Reported recovery actions and retry safety never grant permission; recovery stays Orbi/operator-owned.

Monitoring stays read-only: no merging, Orbi CLI, Git commands, arbitrary shell/path RPCs, or timer/unit mutation invented by this plugin. Service controls are off unless the operator grants named actions on named deployments, and then they run only the operator's own bound lifecycle command (see [service controls](#service-controls-operator-grant-default-off)). No raw logs, prompts, reasoning, or interactive Pi attachment. External Pi sessions are not Paseo-managed sessions. Reading their projected activity does not establish interactive attachment, live steering, token streaming, or that a process is still alive. Future feature work may share entry files and must reconcile edits there.

## Setup

Baseline: Linux, Node **22.19.0**, Paseo daemon and app **0.15.4**. The manifest declares admission `>0.15.0`; that check only gates installing/loading, and installed 0.15.1, 0.15.4, 0.16.0-beta.2 and 0.16.0 rows remain NOT_RUN (#23). Issues uses the daemon user's existing authenticated GitHub CLI. Fleet uses existing user systemd units and does not invoke GitHub; Issues never invokes systemd. No provider/model/auth changes are required or performed.

An operator supplies an existing JSON file via the daemon environment's absolute `PASEO_ORBI_CONFIG`. That variable must be visible to the running daemon/plugin subprocess at startup: exporting it in a later CLI shell does not change an already running daemon's environment. Arrange it through the daemon's existing operator-managed launch environment; the plugin does not alter that launcher or activate services. Authorization, TOML, source compatibility and retention settings are read once at plugin startup; changes require an explicitly authorized plugin reload. **Refresh does not reload configuration.** The plugin does not write configuration or discover repositories. All paths and logins below are placeholders.

```json
{
  "schema": 1,
  "deployments": [{
    "id": "example",
    "label": "Example deployment",
    "repo": "owner/repository",
    "configPath": "/srv/example/orbi.toml",
    "engineSourcePath": "/srv/orbi-source",
    "repoDir": "/srv/example/repo",
    "deployHome": "/srv/example/home",
    "trustedPublisherLogins": ["trusted-publisher"],
    "adapter": "orbi-0.7.41-release"
  }]
}
```

The TOML is parsed as inert data, never imported or executed:

```toml
repo_dir = "/srv/example/repo"
deploy_home = "/srv/example/home"
source_repos = ["owner/repository"]
unit_name = "example"
max_concurrency = 2
```

Paths must be absolute in the JSON, canonical and free of symlink components or environment expansion. TOML paths resolve against its directory and must match those exact roots. One `source_repos` repository must match; capacity is 1..5. `unit_name` is optional (default Orbi units); when present, use letters, numbers, `_` or `-` (maximum 80 characters). IDs match `^[a-z][a-z0-9-]{0,63}$`; labels have 1..80 printable characters. At most 16 deployments; IDs and GitHub repositories are unique (repositories case-insensitively). No credentials belong in the authorization file. Unknown JSON fields are rejected. An optional per-deployment `controls` object grants service actions; without it that deployment stays read-only.

`server/compatibility.ts` enumerates the finite inspected files and manifest hashing algorithm. This is compatibility evidence for that subset, **not authentication of the engine**, and neither version strings nor Git metadata grant trust. The plugin never imports or executes engine source.

### Failure and repair

- Missing `PASEO_ORBI_CONFIG`: `unconfigured`, no entries; UI explains operator setup.
- Malformed file, invalid identity, duplicate ID/repository, or over 16 entries: global `invalid`, no entries. Repair the operator-owned authorization and reload.
- Mismatched TOML, missing/unsafe roots: entry-local `invalid_config` with a safe code. Correct the exact authorization/TOML; do not broaden access to make it pass.
- Unknown/missing/modified source subset: entry-local `unsupported_source_profile`. Use a supported unmodified source checkout or wait for a separately qualified adapter, then reload. Other valid entries remain usable.

The RPC returns only IDs, labels, repository names, adapter names, status and allowlisted problem codes. It never returns private roots, publisher logins, environment values or raw error prose. Invalid entries cannot resolve into read capabilities. No `.orbi/env`, provider, Git metadata or lock reads are permitted. Config, TOML, source and approved JSON reads are bounded to 256 KiB and a 10-second caller deadline, and reject nonregular files and symlinks, with opened-file identity checks to narrow check/use races. Startup directory checks use the same 10-second deadline. Disposal aborts initialization as well as pending port reads, clears their deadlines, and closes handles; a stuck kernel filesystem operation itself cannot be forcibly cancelled, so late completions are discarded and late-opened handles closed.

Internal process ports allow only fixed `systemctl show`, bounded `journalctl`, and GitHub.com `gh api --method GET` forms. Shell is off, stdin ignored, two children maximum, 10 seconds and 1 MiB combined output per child; timeout and disposal kill each operation's isolated Linux process group (including helpers holding output pipes), then reap the direct child. Internal raw output is not a public RPC. The GitHub reader validates and projects it before transport; future collectors must do the same. Caches are memory-only. Client observations poll mounted foreground/connected surfaces every 30 seconds, coalesce refreshes, retain failed data as stale, mark it stale after 60 seconds without success, and guard cancelled host/deployment generations.

## Data flow and permissions

The operator authorization grants narrow read capabilities inside this plugin; it is **not an OS sandbox**. Server and preparation code run with the daemon user's filesystem/process/network access, and client code runs in connected Paseo apps. Trust the code, dependency and future updates before consenting to installation.

Local authorization/TOML/source, health/run/session records, fixed systemd properties and bounded journal data are projected on the daemon. Only validated fields travel over Paseo RPC to the selected host's clients; observations/cursors are memory-only. GitHub.com receives fixed read-only API requests via the daemon user's existing `gh` authentication. That identity needs repository metadata, issues/comments/dependencies, PR and checks read access for the selected repositories; no new token or write permission is requested. Private-repository access must already be authorized. Authentication repair is external, not a plugin action.

Preparation downloads only the locked runtime TOML parser (`smol-toml` 1.9.1) from npm, with project/dependency lifecycle scripts disabled. Runtime observation downloads/installs no software and sends no prompts or tool results to agent providers. There is no plugin-owned persistent cache, telemetry service or raw-log transport. Read-only means no runtime/config/GitHub mutation by this implementation, not a promise that trusted plugin code lacks the user's underlying privileges.

## Issues and GitHub authentication

Open **Orbi → Issues**, select an available repository in the catalog, then browse pages or select an issue to inspect its reports and native blockers. Browsing defaults to **Open** issues and offers **Closed** and **All states**; the chosen state is a server-side GitHub query parameter, never a local filter over one all-state page. A **label** control applies exactly one literal label (the `ai-ready`, `ai-planning`, `ai-blocked` and `ai-in-progress` shortcuts, or any other label typed into **Exact label filter**); the value is bounded, validated and URL-encoded as GitHub's `labels` parameter, and an invalid value (over 100 characters, a leading space, or a comma that GitHub would read as a list separator) never reaches `gh`. Changing state or label returns to page 1 and discards the previous selection. Issue rows show the repository's literal label names as wrapping GitHub-style chips using the label's validated six-digit color and a contrast-adjusted foreground; a missing or invalid color falls back to one neutral chip color, and names alone carry the meaning. Enter an exact issue number and choose **Inspect issue** to read that issue's detail directly, including closed/merged issues and issues outside the ten-page window; a looked-up issue is its own detail section and not a browse-page membership claim. Rejected deployments remain visible with their diagnostics, never selectable. Each repository is read separately on the selected host. The typed `issues.list({deploymentId,page,state,label?})` and `issues.get({deploymentId,issue})` RPCs expose validated projections only: no bodies, comments, credentials, activity targets or check output.

Use the separate **Open on GitHub** link to deliberately open an issue or an available attributed PR. Links accept only the exact canonical GitHub destination for the currently selected catalog repository and issue/PR number; invalid, foreign or conflicting identity stays noninteractive text. Opening does not inspect an issue, change pages, make an extra RPC or mutate GitHub. Source, reported/verified and stale badges keep their meaning; retained stale evidence is navigable only for its still-selected repository. Paseo's `ExternalLink` uses the system browser on Electron, a new `noopener,noreferrer` tab on web, and the OS URL handler on native. A resolved opener does **not** prove the page opened or loaded, and popup blocking cannot reliably be detected. A rejected opener shows only “Could not open GitHub. Try again using the link.” Retry explicitly after checking the platform's browser/URL handler. Selection changes replace/remove mounted links and clear their error feedback; the SDK cannot revoke a retained old callback or cancel an already-dispatched open. Offline fixtures verify validation and opener invocation, not a real browser/OS launch; actual opening remains unrun pending the #12/#13 browser/native qualification gates.

Authentication belongs to the operator and the daemon user's existing `gh` context, not plugin settings. The plugin does not extract tokens, source `.orbi/env`, authenticate, or change permissions. It runs only fixed `gh api --hostname github.com --method GET --include` requests with `Accept: application/vnd.github+json` and API version `2022-11-28`, without CLI caching or verbose output. Endpoints are constructed from authorized repository identities and validated positive issue/PR numbers; supplied URLs are never fetched. Only repository issues, selected-issue comments/details/dependencies, exact-repo PR metadata, and that PR head's check metadata are read.

Lifecycle precedence is: verified associated PR merge or `ai-merged`; closed without merge evidence; `ai-blocked`; `ai-needs-detail`; `ai-epic`; reviewing (`ai-awaiting-merge`, `ai-pr-opened`, `ai-fix-needed`, with the specific label badge); `ai-in-progress`; `ai-planning` / `ai-paused`; `ai-ready`; Other. `ai-human-review` alone is not a wait state. Conflicting lifecycle labels remain visible as evidence warnings. A selected issue's newly read facts update its displayed group. Labels and receipts are **reported**, not verified merge evidence: verification requires the authorized PR's `merged_at`. GitHub terminal/manual facts outrank reported progress. Ready candidate never promises pickup; dependencies remain unknown until requested, and unavailable/incomplete dependency reads never mean unblocked. Foreign-repository dependencies are unavailable rather than incorrectly attributed locally.

Browsing uses numbered pages of 100, sorted by updated time descending, excludes PR objects, and explicitly does not establish active membership. Observation and cache identity include the repository, state, exact label and page, so one filter's page can never be served as another's; a page that contains only pull requests still offers **Next page** instead of claiming no issues. The server-only `GitHubReader.listIssueScope` completely paginates **open** issues for Runs/Blockers; consumers must check `complete`. Collections stop at ten pages or 60 seconds, with child deadlines reduced to the remaining cycle budget. A cap/failure never installs partial active membership or a new current run. Previous complete evidence is retained stale, or an initial incomplete result has no established members/run. Detail reads are on demand, not a sweep of historical issue comments. Identical requests coalesce and use a bounded memory-only, 30-second cache. An incomplete detail refresh can still show a newly confirmed closed/terminal fact while retaining explicitly incomplete report evidence. Report selections carry safe typed problems (including comment authentication failures), which also appear on the detail observation. A failed refresh of the same run's associated PR retains its previously verified merge stale; a different or conflicting identity cannot borrow that verification.

Formal metadata follows the [pinned public contracts](https://github.com/orbi-build/orbi/blob/fbafd09fe49a20299e96565f100633bca61ae2af/docs/public-contracts.mdx). Only configured `trustedPublisherLogins` authenticate publication; `authorAssociation` and copied markers grant no trust. A formal run prefix selects the newest updated run (numeric comment-ID tie break), then that run's newest progress. A newer missing/invalid report never borrows an older run. The reader validates the closed progress/failure/base-CI vocabularies and scene schema, strips every activity target, and does not parse arbitrary prose. The pinned base-CI writer's final block is accepted only on its formal validated base-CI failure, excluding quotes/fences. Legacy prose is missing; unknown versions are unsupported. Attribution includes repository, issue, REST comment ID and update time.

A selected run's formal merged comment must carry one unquoted details block with all six unique fixed machine rows. Duplicate/missing/malformed rows, invalid commit/numeric values, mismatched run IDs and foreign PR URLs are invalid. A valid receipt can identify a PR without a scene; conflicting valid scene/receipt identities expose **conflict**, with no selected PR. A malformed present source cannot disappear behind a valid fallback. Runs and Blockers should reuse `readIssueReports` and the server-only `getPullRequestEvidence` helper/method rather than reparse receipts.

### GitHub failure and repair

- `auth_denied`: no empty/ready success. Ask the operator to repair the daemon user's `gh` authentication/repository permissions outside the plugin, then Refresh.
- `rate_limited`: wait for `Retry-After`, rate-limit reset, or the 60-second fallback. All GitHub reads on this plugin installation share the gate; manual Refresh cannot bypass it. A 403 without quota exhaustion is `auth_denied` and also applies backoff.
- `not_found` on dependencies: unknown/unavailable, not an empty blocker set. Check repository access/API availability outside the plugin.
- `network_failed`, bounded process/read failures, `invalid_response`, `deadline`, or `incomplete`: retain previous complete evidence stale and retry after repair/the polling interval. Do not broaden authorization or infer an empty queue.

Offline fixture tests exercise the registered RPC, real reader and React Native screen path, including auth failure/repair, pagination, stale retention and forbidden canaries. A separate Playwright fixture preview exercised the actual screen components with React Native Web, registered RPCs and a bounded fake-gh executable at desktop/tablet/mobile widths (light/dark), including auth failure and repair/Refresh, with no browser errors or horizontal overflow. Neither is live GitHub or installed Paseo qualification; those remain separately authorized live checks, not part of offline qualification. No installation, credential change or GitHub mutation is part of this feature.

## Runs and log privacy

Open **Orbi → Runs** on the intended host, select an available catalog deployment, then select a run for detail evidence. Rejected deployments retain their diagnostics and cannot be selected. On a confirmed unconfigured host Runs shows one instruction, **Link a repository to see its runs.**, with the one shared **Setup guide**, no GitHub-issues setup copy and no `runs.list` read; loading, invalid, rejected and unavailable catalogs keep their own repair copy instead of being labelled unconfigured. `runs.list({deploymentId,issue?})` and `runs.read({deploymentId,issue,runId})` accept only deployment/issue/run identities, never paths, commands or cursors. Keys include deployment, configured repository, exact issue number and eight-hex run ID. Summary screens poll every 30 seconds while foreground/connected; event/PR detail loads only on explicit selection or its manual **Refresh**, with observation time visible. Host/deployment/issue changes and unmount discard late results and release owned timers/children.

An Issues detail or a Blockers evidence row whose report read is complete and establishes a selected run shows **Reported run** as an activatable control. It reopens this Runs screen for the same deployment with screen params `deploymentId`, exact `issue` and eight-hex `runId`: the issue-history filter is preselected and the run detail opens once, and only after the existing `runs.list` observation contains that run. A run missing from the observed history is never selected or looked up; the screen says so and Refresh is the repair. Absent or invalid params render the unchanged Runs screen and select nothing, and params add no RPC, no read and no persisted state.

Active rows require the **last complete successful open-issue scope**, an Implementing/Reviewing lifecycle and the trusted report reader's selected run identity. Terminal/manual states (including Blocked) win over progress. An initial incomplete scope establishes no members; a failed refresh retains the last complete scope visibly stale. A newer report without progress never borrows another run's stage. Local directories alone cannot create active rows or prove liveness. Enter an exact issue number and choose **Inspect issue history** to inspect local retained runs separately; history is never labeled active. Old runs without selected trusted PR identity do not borrow a newer run's PR.

Discovery is confined to `<repoDir>/.worktrees/orbi-<owner>-<repo>-issue-<N>-<8hex>/`, with exact 42/420 separation. More than 200 matching entries per requested scope or 16 JSONL sessions per run yields `read_limit`, not an arbitrary filename/mtime-selected subset. Run-state repository/issue/run/branch must agree with that attribution; its `worktree` field is never followed. `created_at` is a recorded timestamp, **not a guaranteed start time**. Branch, pushed SHA and reviewed SHA are evidence values, not process-state probes.

Session reads validate the complete first header within 64 KiB and read at most 256 KiB tail/increment per session, with 64 KiB records. In-memory offsets reset on observed truncation/replacement. Incomplete fragments are dropped; malformed data or missing identity means **unavailable activity, not idle**. Only session ID, activity timestamp and `read|edit|command|analysis` kind cross the boundary. No prompt, reasoning, message, tool arguments/targets/output, raw session/journal/test logs or command/path text is exposed. There is no terminal embedding, session creation/attachment, Git read/fetch, process signaling or lock probing.

The fixed journal query is `journalctl --user -u <authorized-service> --no-pager --since '-1 hour' -n 200 -o json`, independently for configured slots. JSONL plus strict Orbi grammar permits only exact scoped `run_start`, `run_end`, `worktree_cleaned` and (installed profile only) `worktree_retained`. Prefix and run/issue fields must agree; duplicate/ambiguous fields and free-text tails are rejected. Only journal `__REALTIME_TIMESTAMP`, event, run ID and issue number are projected, at most 200 events / 64 KiB. Ticket-only `run_end` need not carry PR/commit. Failure details belong to structured reports, never `run_failed`/heartbeat parsing. This bounded window always reports `journal: incomplete`: gaps/rotation are not fabricated into continuous history.

PR identity comes **only** from Issues' trusted `readIssueReports.prIdentity`; missing/invalid/conflicting identity triggers no guessed lookup. PR number/URL/state/`merged_at`/`head.sha` and safe check name/status/conclusion/GitHub URL are evidence, never check output/annotations. Only checks explicitly matching that observed head qualify it; absent, missing, pending, inaccessible or stale-head checks are **not passed**. Reported stage `checks` is not test success.

For `auth_denied`/`rate_limited`, follow [GitHub failure and repair](#github-failure-and-repair). For filesystem `read_failed`, `invalid_response`, `incomplete` or `read_limit`, inspect the attributed writer/retention externally, repair it without broadening authorization, then Refresh. Refresh never repairs files or controls Orbi. These limits are planner bounds, not inherited Orbi latency promises.

Offline tests compare fixture tree/content/metadata before/after observation (excluding atime), assert canary suppression, exact process argv, head-check states and teardown. A Playwright preview exercised the real registered Runs component and typed RPCs with bounded inert gh/journal/file fixtures at desktop/tablet/mobile widths, including auth failure → external repair → Refresh, without browser errors or horizontal overflow. Screenshots are run artifacts. This is **not** live-log-format, installed Paseo or native-mobile qualification; no real agent turn/Orbi process was started.

## Blockers and recovery limits

Open **Orbi → Blockers**, select an available deployment, then **Inspect artifact metadata** on an issue. Enter an exact issue number and choose **Inspect issue** to see why that issue is or is not in the attention scope, including **No current blocker label observed** for a non-candidate; a looked-up issue is not a blocker-scope or page membership claim and never changes the candidate page or `hasNextPage`. Rejected catalog entries retain their safe diagnostics and never grant reads. `blockers.list({deploymentId,page})` returns an `Observation<BlockerPage>`; `blockers.read({deploymentId,issue})` returns an `Observation<BlockerDetails>`. Selectors are positive integers, with no path or command input. Runs is not a prerequisite.

The shared GitHub reader establishes complete open membership before classifying candidates with `ai-blocked`, `ai-needs-detail`, `ai-fix-needed` or `ai-awaiting-merge`. Pages contain up to 20 candidates; only that page's reports are read, not unrelated/historical comments. Manual attention, automatic fix/review pending, and maintainer merge wait are separate, not all terminal failures. Above the rows, one labelled count per attention class summarises only the records this observed page returned (at most 20 candidates) — never a repository total; an incomplete/retained-membership page says so and an empty page shows no counts. Rows render manual attention, automatic fix/review pending, maintainer merge wait, then GitHub terminal, keeping the observed page order inside a class. Detail shows current GitHub state/labels and their update time, selected run, report status, repository/issue/comment attribution and source links. Closed/merged GitHub facts make retained failure reports historical. Conflicting labels remain visible.

Only the selected run's trusted formal failure schema 1 supplies outcome (`blocked` / `fix_needed`), the closed reason/action enums, and strict boolean `retry_safe`. Explanations are plugin-owned, including legacy `tests_failed`. Missing, invalid, unsupported or unknown metadata never falls back to free-text diagnostics. **Reported retry safety is metadata, never permission to retry.** Base-CI `waiting`, `resuming`, `merged` and `stale` remain separate reported states; resuming is not delivery success, and reported merged does not independently verify delivery success. Source: [pinned failure vocabulary](https://github.com/orbi-build/orbi/blob/fbafd09fe49a20299e96565f100633bca61ae2af/src/orbi/failure.py#L45).

For a complete, valid, exact-run scene with nonconflicting repository PR identity, the server derives the pinned `gitops.worktree_path` name under the authorized repository's `.worktrees`. It does not use a supplied scene path, enumerate directories, scan alternate roots, or search renamed worktrees. Only the worktree directory and `.orbi/run-state.json`, `.orbi/test.log`, `.orbi/plan.md`, `.orbi/verify.md` are metadata candidates. The port performs bounded `lstat`/canonical-path checks, rejects symlinks/nonregular artifacts, and exposes only a fixed relative name, presence status, byte size and modification time. Sizes are stat sizes, not recursive worktree totals. No artifact is opened or read; even run-state contents are not inspected as proof of identity. Missing, unreadable, invalid, present and unattributed evidence remain distinct. No absolute scene paths, artifact contents, raw failure diagnostics, prompts, tokens or downloads cross the RPC boundary. A missing/cleaned scene never removes a GitHub blocker or triggers recreation/cleanup.

Retention settings are inert startup observations, not promises:

| Profile | Supported settings/defaults | Limit |
| --- | --- | --- |
| `orbi-0.7.41-release` | `worktree_retain_hours = 72` (finite positive number); `keep_failed_worktrees` unsupported and ignored | Official v0.7.41 may delete terminally failed worktrees |
| `orbi-0.7.41-1a8b2f96`, `orbi-0.7.48-release` | `worktree_retain_hours = 72`; `keep_failed_worktrees = true` (strict boolean) | Failed-worktree retention is a policy, not a presence guarantee |

Invalid supported values reject that deployment as `invalid_config`; repair configuration externally and authorize a reload. **72 hours does not imply automatic reclamation of an open blocked scene.** Only observed presence is reported. ## Fleet

This section covers the host-scoped **Services** screen (the `services` route) and the configured-repository detail the existing `fleet` route keeps on Work.

Open **Orbi → Services** on the intended host (a host without linked repositories lands there). Services answers the service question without a tap: **Services · <host>** names the selected host once and every observed group is listed failures first.

Only current complete/partial evidence publishes the failed-group attention count, and a partial reading qualifies it as observed groups (**1 of 3 observed groups needs attention**) rather than a host total; only a current complete empty check says **No Orbi units found**, while a partial empty reading says **Partial · no units confirmed; units may be missing.** and undecided states claim neither. After a failed refresh or disconnect every retained row is marked **Last seen** with the last successful time even when the header is offscreen, publishes no current count, and the marker clears on the next successful read; a host switch keeps no other host's rows or markers. Off means activity unknown and offers **Set up service access**, not Refresh or counts. Groups remain sorted failed first, then running, timer waiting and other, with stable exact-label ties. A failed group names its first failed slot and unit kind (**Slot 3 · Worker failed**, or **Worker failed** for a non-slot unit) plus a remaining count; readable facts are **Running**, **Idle**, **Timer waiting**, **Installed** or **Unknown / transitional**. Running requires active/running service evidence; Idle requires every service instance in the group to be observed loaded and positively inactive/dead, so an active/exited, activating, not-found, unfamiliar/error or not-observed worker keeps the unknown or transitional fact instead. Worker and timer facts change independently: Running, Idle and Timer waiting can coexist, and a failed slot is named without attributing another running worker to it.

There is no row accordion, chevron or hidden inventory: every observed group is visible with its **Details** and (when uniquely authorized) **View repository** actions. **Details** opens a separate host-scoped view that resolves the selected group again from this host's current evidence, so a label that left the evidence says **This service is not in the current host evidence** and shows no raw data; a passed unit or path is never authority. The view leads with the existing safe display name, then the failed-first numeric slot summaries with both subjects in reading order — **Slot 3 · Worker failed · Timer not observed** before **Slot 1 · Worker idle · Timer waiting** — and the last-success time when the evidence is retained. One short association line follows them: **Not linked to a repository.** only when this host's repository catalog was actually read (configured, or confirmed unconfigured), otherwise **Repository link not confirmed** with the missing catalog read named, so a failed, invalid or still-loading catalog never reads as an unlinked service. The shared repository notice, its **Setup guide** and the raw unit data are not shown here; they stay on the list and other screens. **Unit activity does not establish issue delivery** stays beside the facts, and the authorized **Actions** disclosure (when the operator granted one) stays on this view with its confirmation. **View diagnostics** is closed by default and reveals, in one activation with no additional read and no mutation, the existing slot explanation (**The timer schedules a check. The worker runs it.** and that both are two parts of the same slot, not two workers; a group without a numeric slot gets none), the full association context and the exact original unit names with their raw runtime/unit-file states. Its accessible expanded state follows the disclosure, and a new selection starts closed again so no other service's diagnostics or facts persist. A waiting timer is a timer fact only: it does not establish a queued issue, and starting the worker changes only the worker fact. Unobserved counterparts, unknown runtime and transitional states remain explicit and stay attributed to the worker or timer: a counterpart absent from the inventory says **Worker not observed** or **Timer not observed**, not missing; partial/truncated reads do not prove absence. An explicit not-found load is shown as **not found**, while unfamiliar/error loads retain their load and runtime states. **Back to services** stays available above the facts and returns to the same list at the position it was left at. Opening the view performs no read and no control action. **Refresh services** rereads only host inventory; it neither reads nor configures the repository catalog.

Observed unit activity is not an active delivery, and this section attributes no issue: an unattributed family stays **Unlinked** unless the selected-host catalog is confirmed unconfigured, where one explanation above the rows replaces the repeated badge, and reported PR/issue history is never converted into a process status. The Services attention line describes observed service problems, not repository blockers, and performs no per-repository read.

Association is display-only. A family whose unit prefix uniquely and exactly matches one validated, available configured deployment says so and offers **View repository**, which opens Issues with that deployment selected in one activation; Runs and Blockers keep that selection on the same host/repository. Unit origin is not verified. A configured declaration rejected only for an unsupported source profile is explained as a compatibility limit — not a broken runner — and grants no detail. Duplicate claims are explained as ambiguous. Every other discovered family is explained as discovery-only, with **no disabled action** pretending to be a repair. A matched prefix whose deployment is missing from the current authorized catalog offers no action until authorization is restored, because missing, invalid and rejected catalogs still block every privileged read on every route (and never hide opted-in host inventory).

**Configured repositories** contains the existing rich Fleet section. It is collapsed by default and does not mount or poll Fleet while closed. An explicit `deploymentId` deep link opens it initially; it can still be collapsed. Its state resets on host or deployment selection changes. When expanded, configured deployments stay listed even when this host check did not observe them, marked **Not observed in this host service check** (or **Observed in this host service check**). That observation marker appears only for a check that produced host evidence (`complete`/`partial`). A check that is off, denied or unavailable makes no observed/not-observed claim, and its attempt time is never reported as this host's last successful check or reused as a retained successful observation. While **Configured repositories** is open, only one deployment detail loads: the selected `deploymentId` or the expanded row. Other repositories are listed without a read.

The remaining Fleet evidence below applies to that one loaded detail. Every catalog entry stays listed, including rejected entries with safe diagnostics and repair guidance. Only available entries call `fleet.read({deploymentId})`; the server resolves that ID against startup authorization. No paths or command strings come from the client.

Each loaded detail reports repository/profile identity, configured capacity (1..5), **Occupancy: unknown**, and **Active deliveries: unknown**. Neither active labels nor leftover PID/lock files establish occupancy. Capacity is not a machine-wide promise. **Show details**/**Hide details** (with `expanded`/`selected` state) load one detail at a time, and **View active work in Issues** opens Issues with that deployment filter.

For instances `1..max_concurrency`, Fleet independently reads `orbi-<unit_name>@<instance>.timer` and `.service`, or `orbi@<instance>` when `unit_name` is absent. The fixed read is `systemctl --user show <authorized-instance> --property=Id,LoadState,ActiveState,SubState,UnitFileState,Result,ExecMainCode,ExecMainStatus,NRestarts,LastTriggerUSec,NextElapseUSecRealtime,NextElapseUSecMonotonic --no-pager`. No `Environment`, `ExecStart`, unrestricted properties, control commands, locks or PID probes are requested. Only safe state fields and recognized trigger timestamp strings reach the UI; unknown/missing fields remain unavailable. Monotonic trigger values are not guessed into wall-clock times.

Each slot's `.service` worker and `.timer` are paired by the numeric instance in those observed unit IDs, never by response order, and one accessible summary line per slot in numeric order precedes that slot's raw fields — for example **Slot 1 · Worker idle · Timer waiting · Next trigger Sat 2026-11-14 22:30:00 UTC**. The summary repeats the reported real-time trigger verbatim with its timer context, reads **unknown** or **not found** when a fact is missing or unreadable, keeps unfamiliar active/sub-state pairs verbatim, never turns a unit-file state into a runtime state, and shows a failed worker and an inactive timer as separate facts. Grouping is display-only and adds no read: a waiting timer is not a worker start or an issue pickup.

Recorded health comes only from bounded `<repoDir>/.orbi/health.json` reads, validated against the two pinned writers' `runs`, `last_pickup_ts` and `alerted` shape (at most 50 runs). The public projection contains only last pickup and run repository, issue, run ID, reported outcome and timestamp, never raw health JSON, alert keys or fingerprints. Missing/corrupt files are **unavailable**, not an empty successful history. Reported run outcomes are separate from current service state: `inactive/dead` with `Result=success` is not a failed service. No issue pickup is inferred from timers.

**Workspace shortcut (presence and type only).** A deployment entry may carry one optional shortcut descriptor in the authorized JSON:

```json
{ "id": "demo", "repo": "Example/project", "workspaceShortcut": { "directory": "/srv/aliases/demo", "name": "checkout" } }
```

`directory` must be a canonical absolute parent dedicated to that name (at most 4096 UTF-8 bytes and 64 components, no dot segments, empty components or `/`), and `name` must be 1-128 ASCII characters starting alphanumeric and otherwise alphanumeric, dot, underscore or hyphen. Nothing is validated against the filesystem at startup, no path comes from the client and there is no default. A malformed descriptor disables only the shortcut (`config: shortcut_invalid`) and never changes deployment authorization, other entry fields or schema-1 compatibility.

Selection alone reads nothing. One **Inspect shortcut** press is one `workspace.shortcut({deploymentId})` request and one further **Refresh shortcut** press is one more; there is no polling, no inspection while the detail is mounting, and a result that belongs to a replaced host, deployment or repository is discarded. The RPC returns only `{deploymentId, state, observedAt, problem}`: **Symlink present** (`symlink`, including a dangling link), **Present, not a symlink** (`not_symlink`), **Not present** (`absent`), **Cannot inspect** (`cannot_inspect`) or **Not configured** (`not_configured`). No path, target, inode or error string is transported or displayed.

The server requires Linux with the real `O_DIRECTORY`/`O_NOFOLLOW` constants and genuine procfs at `/proc`, acquires `/` and each configured component with held directory descriptors (`/proc/self/fd/<parent-fd>/<component>`, no-follow), and then observes **only the named leaf** with `lstat` relative to that held parent. It never calls `readlink`, never opens the leaf, never resolves, follows, compares or displays the target, never enumerates the directory and never writes. Only a final `ENOENT` under an established, revalidated anchor is **Not present**; a missing or unsafe parent, a symlink or non-directory component, denied access, unsupported routing, a stalled lookup or any other indeterminate error is **Cannot inspect**. One inspection runs at a time with a 1000 ms budget; a second press while one is outstanding answers **Cannot inspect** with `filesystem: read_limit`, and a timed-out lookup keeps its reservation until it settles and its descriptors are closed (`filesystem: deadline`).

Repair: `config: shortcut_invalid` means the descriptor needs an operator fix plus an authorized reload. `filesystem: not_found`/`unsafe_path` means the configured parent is missing, replaced by a symlink, or not a directory. `filesystem: read_failed` means denied or unreadable access; do not weaken directory permissions for this feature. `filesystem: runtime_unsupported` means the platform or procfs route is unsupported. A shortcut is a possible convenience for terminal, editor and file-manager users; it is **not** a Paseo workspace registration, and presence never proves that a checkout exists or that the link opens. Mounting the view performs zero inspections. Installed visual and physical-client proof of this block remains NOT_RUN under the unchanged installed-test consent gate.

Details keep independent source problems and timestamps. One inaccessible deployment or failed timer does not remove the others or the host service section. `systemd: process_failed` means that unit read failed; check access to the selected host's user units externally, then **Refresh**. `filesystem: read_failed` means health could not be read/validated; check the health writer/file externally, then **Refresh**. Port deadlines/output limits retain their safe codes. `process_limit` means the foundation's two-child bound was reached; retry Refresh after pending reads finish. Rejected entries require operator configuration/source repair and an authorized plugin reload. Refresh only reads; it never repairs or controls a service.

The shared observation lifecycle polls foreground/connected surfaces (the host service check and the loaded detail) every 30 seconds. A failed refresh preserves previous data with a stale badge; after 60 seconds without success, data is visibly stale. Detail timestamps remain visible; compact host inventory shows last-success time when stale. Text uses theme tokens and compact layouts wrap within the viewport. These are design bounds, not measured performance claims. No new fleet daemon or scheduler is required.

Shared observations declare descriptive loading/status accessibility labels and a stable alert region containing only safe problem source/code summaries, separate from timestamps and retained data. Age/offline staleness alone does not invent an error. Detail views keep **Refresh**; the host service section names its inventory-only read **Refresh services**. Both show Refresh/Refreshing and are disabled with dimmed theme-colored text and disabled/busy accessibility state while the selected host is offline, the app is backgrounded, or a read is in flight. ## Host service inventory (opt-in)

A separate host-scoped, read-only `services.inventory({})` RPC can discover Orbi-named user service and timer candidates even when this host has zero authorized repositories. Disclosure is opt-in at plugin startup only: `PASEO_ORBI_HOST_INVENTORY=1` in the daemon's launch environment permits connected clients on that host to read it; any other value leaves the RPC `off`, spawns nothing and reveals nothing. It is independent of `PASEO_ORBI_CONFIG`, and a later environment change needs an explicitly authorized reload. Nothing is enabled by default.

The inventory executes exactly two fixed reads and nothing else:

```
systemctl --user list-units --all --type=service,timer --plain --no-legend --no-pager --full 'orbi*.service' 'orbi*.timer'
systemctl --user list-unit-files --type=service,timer --no-legend --no-pager --full 'orbi*.service' 'orbi*.timer'
```

The literal globs are single argv elements; shell is off, stdin ignored, and `LC_ALL`/`LANG` are `C` with `SYSTEMD_COLORS=0`. Both reads share the existing two-child cap, 1 MiB combined stdout/stderr ceiling, per-child timeout and process-group kill/reap, plus one overall 10-second deadline: a child that reaches the byte or time limit is stopped and the second read is not launched after the deadline. There is no system-manager or other-user access, sudo, broad process scan, `systemctl show/cat`/`Environment`/`ExecStart`, journal read for discovery, guessed file path, installed symlink follow or GitHub request. A discovery name match never becomes a repository read capability.

Rows are parsed from validated `ID LOAD ACTIVE SUB` (loaded runtime state) and unit-file `ID state` (installed names) only; descriptions, vendor presets, paths, environment and stderr are never stored or transported. Service and timer sightings are deduplicated by ID while keeping per-source availability, and runtime and installed facts stay separately nullable: a timer schedule is never reported as runner execution, and an installed name is not a running service. Units are grouped by sanitized unit-family prefix with kind `runner-family`, `auxiliary` (the known `orbi-exporter`) or `other` (other safe orbi-prefixed names). Default/named templates and their observed slots stay in one group; unpaired service/timer records are retained; no slot, occupancy or authentication claim is synthesized.

Association is display-only. A group is `matched` (and only then carries a deployment ID) only when its prefix uniquely and exactly equals the expected runner prefix of one validated, available deployment declaration. A configured declaration whose sole rejection is an unsupported source profile shows `incompatible` with no selectable deployment ID and its observed units are still listed. Duplicate prefixes — including a supported/unsupported collision — are `ambiguous`; other, auxiliary, unmatched or out-of-profile names stay `unmatched`; none grants repository authority or bypasses `ConfigRepository.resolve`.

The response is `off`, `complete`, `partial` or `unavailable` with observation time, per-source completeness/observation times and fixed problem codes (`malformed_record`, `process_failed`, `process_timeout`, `process_limit`, `read_limit`, `row_limit`, `deadline`, `disposed`). At most 256 accepted rows are retained per inventory, sorted deterministically before display; a cap or any failed source is incomplete rather than a confirmed empty result, and no total is invented. A `complete` empty group list is the only confirmed "no Orbi-named user units observed" result. One host-level snapshot is coalesced across concurrent callers and cached in memory for at most 30 seconds with no disk state and no repeated reads per family or viewer.

**Revocation.** The startup grant ends when the operator disables, removes or reloads this plugin, or stops the daemon. The plugin lifetime aborts: the in-memory snapshot is discarded, a read still in flight is abandoned before its next `systemctl` call, late output from an already-running read is never parsed, returned or cached, and later `services.inventory({})` calls answer `off` with zero host reads. Services replaces the families it had observed with **Service check off · activity unknown** when it receives that answer; former unit names are not retained as stale rows.

**No in-app Save on the pinned host.** The pinned native plugin settings surface exists, but session admission at the pinned and published versions grants every admitted client owner permissions, plugin observation and settings mutation share the `daemon.manage` capability, and the plugin handler context carries no independent authenticated operator identity. A settings write therefore cannot enforce viewer denial, so this plugin keeps the startup-only operator opt-in and offers no Save control, settings toggle or settings-write RPC. A per-host setting returns only when a supported host-enforced operator/viewer boundary exists and a real host proves operator allow and viewer deny; a client flag, hidden button, revision number or plugin-specific token is not that boundary. The same missing boundary is why service controls are a startup-only operator grant that must state `admittedClientsOperate`, and why no in-app grant, role switch or action history is offered.

Repair: `process_failed` (including authorization/DBus failures), `process_timeout` or `process_limit` means the selected host's user `systemctl`/DBus access or child limits need external repair, then call again after the snapshot window (or reload for a startup opt-in change). `malformed_record`/`row_limit`/`read_limit` mean the host output exceeded the bounded parser/limits; do not infer an empty inventory. This RPC reports user-unit candidates only; it never controls, enables, disables or restarts a unit.

The **Services** screen consumes this snapshot as host evidence (`client/shell.tsx`, `client/host-overview.tsx`), sorted and explained in [Fleet](#fleet); Work shows only the one-line health summary as text beside its separate **View services** action. It keeps the host-qualified observation key, and is disabled with zero reads while the selected host is offline, the app is backgrounded, or a check is in flight. A cancelled host generation cannot publish into another host with the same family label and slot, and a host switch discards the previous host's selected diagnostic view. With inventory off, Services keeps the catalog/setup/deep-link behavior, shows no discovered families and clears families it displayed before an off answer arrived.

## Service controls (operator grant, default off)

A deployment is **read-only unless the operator grants controls on it**. The grant is part of the operator-owned startup authorization and is read once at startup, exactly like every other setting: changing it needs an explicitly authorized plugin reload, and no client, Refresh, or in-app control can grant, widen, or extend it. Absent `controls`, `deployments.list` reports `controls: null`, the diagnostic view shows no Actions control and `services.control` answers `denied`/`action_not_approved` without running anything.

**Trust model this grant states explicitly.** At the pinned and published Paseo versions, ordinary session admission grants every admitted client owner permissions, plugin RPCs share the `daemon.manage` capability, and a plugin handler is given only `{ paseo }` — no authenticated operator identity, no viewer/operator split. A viewer cannot be denied while an operator is allowed. The grant therefore requires `"admittedClientsOperate": true`: an explicit statement that every admitted client of this host may operate the approved targets. Do not grant controls when that is not acceptable; the plugin offers no client role flag, hidden button, caller-supplied identity or plugin token as a substitute for the missing host boundary. **An actual host authorization proof (operator allow, viewer deny) has not been run and is not claimed.** Recording the authenticated actor is likewise impossible here, so each result records `actor: null` instead of inventing one.

```json
{
  "schema": 1,
  "deployments": [{
    "id": "example",
    "label": "Example deployment",
    "repo": "owner/repository",
    "configPath": "/srv/example/orbi.toml",
    "engineSourcePath": "/srv/orbi-source",
    "repoDir": "/srv/example/repo",
    "deployHome": "/srv/example/home",
    "trustedPublisherLogins": ["trusted-publisher"],
    "adapter": "orbi-0.7.41-release",
    "controls": {
      "admittedClientsOperate": true,
      "actions": ["start", "stop"],
      "commands": {
        "start": ["/srv/example/bin/orbi-lifecycle", "start", "{unit}"],
        "stop": ["/srv/example/bin/orbi-lifecycle", "stop", "{unit}"]
      }
    }
  }]
}
```

Grant rules, all entry-local (`invalid_config` for that entry only):

- `actions` is a non-empty unique subset of `start`, `stop`, `restart`. Anything else is rejected.
- `commands` must contain exactly one array per approved action and nothing else. Each argv has 1..8 non-empty tokens of at most 200 printable characters, exactly one literal `{unit}` token, and an `argv[0]` that is an absolute, canonical path under the same rules as every other authorized root. `{unit}` is replaced only by the server-derived, validated unit name `orbi[-<unit_name>]@<slot>.service`; a caller can never supply a unit, verb, path, argv or environment value.
- Shell is never used: the tokens are passed as separate argv elements, so metacharacters are inert. There is no globbing or expansion.
- `argv[0]` must be the operator's own lifecycle entry point. A grant that names a system-manager or privilege-escalation program directly (`systemctl`, `systemd-run`, `env`, `sudo`, `doas`, `pkexec`, `su`) is refused as `config_mismatch`, so `restart` can never be a raw `systemctl restart` and no action can escalate privilege. A wrapper script the operator owns remains allowed; it is then that script's own behaviour that acts on the unit.

**Lifecycle ownership stays with Orbi.** This plugin never assembles `systemctl` start/stop/restart/enable/disable, refuses a grant whose program is `systemctl`, and never invents a restart sequence. The command above is the operator's binding to the supported Orbi lifecycle: for `start`/`stop` it must be the Orbi lifecycle entry point that preserves the runner's scheduler, draining, ownership checks and explicit pauses. The inspected Kit helper (`orbi_control.py`) exposes `status|setup|start|update|stop` and **no restart verb**, so a `restart` action must be bound to an operator-documented drained sequence; the plugin never substitutes a raw `systemctl restart`. In addition the plugin refuses `restart` unless the slot is observed `failed` or `inactive/dead` with a loaded unit, and refuses when that state cannot be read. A restart therefore never becomes an undocumented kill of an active delivery, and Start/Stop preserve the semantics of whatever Orbi lifecycle command the operator bound.

**One submission per deployment.** Operations are serialized per deployment: a second request while one is in flight returns `pending`/`busy` and submits nothing. The result vocabulary is closed: `succeeded`, `failed`, `unknown`, `pending` and `denied`, always with the bounded reason code and the state re-read afterwards through the ordinary bounded `systemctl show` read. A timeout returns `unknown`/`process_timeout` — never success and never a claim that the submitted job was cancelled. A command that exited 0 but whose state could not be re-read returns `unknown`/`observe_failed`, so the UI never reports an unobserved success. Nothing is retried automatically; the operator rechecks the slot and decides.

Denials happen before any execution: `deployment_unavailable` (unknown, rejected, foreign or stale deployment id), `action_not_approved` (no grant, or this action not granted), `target_out_of_range` (slot outside `1..max_concurrency`), `active_delivery` (restart refused for a running/transitional slot), `observe_failed` (restart state unreadable), `disposed` (grant withdrawn or plugin stopping), `busy` (another operation in flight). Authorization is rechecked immediately before execution, so a grant revoked while an earlier observation was awaited still refuses the action.

**Revocation.** Disabling, removing or reloading the plugin, or stopping the daemon, aborts the grant lifetime: no new action starts, a pending authorization is rechecked and refused, and no result is retained. Each result carries a server-generated operation id, the approved deployment/slot/action and the outcome; no argv, path, environment value or secret is ever transported or logged.

**Evidence limits.** Offline tests cover the grant parser, the adapter (exact target, denial, serialization, timeout/unknown, re-observation) and the Services diagnostic flow (confirmation, single submission, honest outcomes, host isolation) with injected ports and a real bounded child process. **Not run:** an actual host authorization proof, an installed lifecycle binding (no operator-approved lifecycle entry point has been bound and exercised on a host), and any live Start/Stop/Restart against an existing runner. Use only an explicitly approved disposable target with scoped cleanup for a live check — never an existing production worker.

**UI flow.** Expand a linked repository row, open **Actions**, choose an action for an observed slot, and confirm. The confirmation names the selected host, the repository, the exact target (`orbi-example@1.service`) and the effect; confirmation is not authorization, and the daemon rechecks the grant. Every control is disabled while a submission is in flight, results are host-qualified (a result or an action can never appear on another host), and the row falls back to read-only when the catalog has no grant for that deployment.

## Authorized installation (not performed here)

Plugins are trusted, unsandboxed host code. Obtain explicit operator approval before enabling plugins or installing. Once approved, inspect the target daemon's root `pluginsEnabled` switch. If absent/false, obtain separate explicit consent before enabling it; do not assume plugin installation grants that consent. Use the [official direct-Git flow](https://paseo.sh/docs/plugins/publishing.md#share-through-github-or-git):

```sh
paseo plugin add git:TrebuchetDynamics/paseo-orbi
paseo plugin ls
paseo plugin logs paseo-orbi
```

Without `--ref`, Paseo installs the repository's current default HEAD (`main`) at install time, not a GitHub Release. The offline checks do not promise that every `main` commit has passed live qualification. The commands above are instructions only: **none were run for this delivery**. Require `running` on the intended host, then open all five views and exercise selected-host RPC success/failure and Refresh. An existing Git installation stays at its installed revision until the operator reviews and applies `paseo plugin update paseo-orbi`; that update checks the current default HEAD, shows the current and proposed revision and asks for approval, and declining or a failed update keeps the installed content. The daemon host needs Node 22.19.0 and Paseo `>0.15.0` (0.15.4 is the tested baseline); the daemon checks its version before installing or loading the plugin, and a rejected update keeps the installed revision.
